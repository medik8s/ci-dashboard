Key Identifiers (what the numbers mean)

IIB Build ID The primary identifier shown on the FBC Summary tab (e.g., IIB 1187142). This is the Index Image Build number from the fbc-release pipeline. It identifies the exact release candidate catalog that merges RHWA operators with the full Red Hat OCP catalog. This is what QE historically used to test operators before release.
IIB Image Digest The sha256 content digest of the IIB (e.g., sha256:91c5eb524cd7...). Immutable and unique. Shown in the expandable detail panel alongside the IIB build ID.
Git Commit SHA The source code commit in dragonfly/rhwa-fbc that triggered the build (e.g., 831c2ada). Shown as a secondary label next to the IIB ID. Click "GitLab" to see the exact source code diff.
Snapshot Name Konflux immutable build record (e.g., rhwa-fbc-<ver>-20260730-035530-000). Click "Konflux" to see the Snapshot page with full build metadata and component image digests.
Quay Image The FBC build image on Quay (e.g., quay.io/.../rhwa-fbc-<ver>:831c2ada...), where <ver> is the OCP version without dots (e.g., 422, 421). This is the raw RHWA-only catalog, before it is merged with the RH OCP index. Click "Quay" to see the image tags.

Glossary (for new team members)

FBC
File-Based Catalog. A container image that lists available operator versions and their metadata. Think of it as an "app store catalog" that tells OLM what operators are available to install. Each OCP version (4.18, 4.22, etc.) has its own FBC image.
IIB
Index Image Build. The result of merging an FBC catalog with the full Red Hat OCP operator catalog index. The IIB is the release candidate - it mimics what customers will see after the operators are officially released. Identified by a numeric build ID (e.g., 1187142) or an image digest.
OLM
Operator Lifecycle Manager. The OpenShift component that installs, updates, and manages operators. OLM reads a CatalogSource (which points to an FBC or IIB image), discovers available operators, and installs them via Subscriptions.
Konflux
Red Hat's build and release system (successor to OSBS/Brew). Konflux builds container images using Tekton pipelines, creates Snapshots (immutable build records), validates them with Enterprise Contract, and publishes them to registries. The RHWA team's Konflux tenant is "rhwa-tenant" on the stone-prod-p02 cluster.
Prow
OpenShift's CI system that runs automated test jobs. Prow provisions temporary AWS clusters, installs operators using OLM, runs Ginkgo e2e tests, and uploads results to GCS. The dashboard collects and displays these results. Jobs run on dedicated build clusters (build01-build10).
CatalogSource
A Kubernetes resource that registers an operator catalog with OLM. It points to a container image (FBC or IIB) and tells the cluster "here is a catalog of available operators." In CI, we create a CatalogSource pointing to the FBC build image from Quay.
IDMS
ImageDigestMirrorSet. A cluster-level configuration that redirects image pulls from one registry to another. Required because RHWA operator images reference registry.redhat.io paths that don't exist yet (pre-release). The IDMS redirects pulls to the Quay pre-release images.
Snapshot
A Konflux Custom Resource that records exactly what was built: the container image digest, source commit, build timestamp, and labels. Snapshots are immutable - once created, they never change. They are the "receipt" that proves what was built from what source.
Enterprise Contract
A validation framework that checks built images against security and compliance policies before allowing a release. It verifies image provenance (was it built by a trusted pipeline?), signatures, SBOM completeness, and FIPS compliance.
PaC
Pipelines-as-Code. A Tekton component that watches git repositories for push/PR events and triggers the appropriate Tekton pipelines. Pipeline definitions live in the .tekton/ directory of each repository.

How this maps to dashboard tabs

FBC Summary Shows test results grouped by IIB build ID (the index image from the release path). Each card represents one FBC catalog version with all operator test results. The IIB ID is the primary identifier; the git commit SHA is shown as a secondary label.
Job Runs Shows individual Prow CI job executions grouped by FBC image. Each group header shows the IIB ID. Click a row to expand and see OCP version, CSV version, IIB details, and all log links.
Test Results Shows individual test case results (pass/fail) from Ginkgo e2e test suites. Each test is linked to a Polarion test case ID for requirements traceability.
Overview Summary cards showing overall pass rates, recent failures, and operator health across all periodic jobs.
Weekly Report Week-over-week comparison of pass rates and top failing tests, useful for tracking CI stability trends.

How retriggering works (IIB vs FBC SHA)

When you retrigger a job from the dashboard, the system needs to know which FBC catalog image to use. Here is how the two identifiers relate:

What you see on screen The IIB build ID (e.g., IIB 1187142). This is the release candidate number that Or and the team use. It represents the final index image that combines RHWA operators with the full Red Hat catalog.
What happens when you click retrigger The dashboard automatically sends the FBC commit SHA (e.g., 831c2ada...) to Prow. You never need to know or type the SHA. The button already carries it behind the scenes because each IIB maps to exactly one FBC commit.
Why not retrigger with the IIB directly? Prow CI uses the raw FBC build image from Quay (tagged by commit SHA), not the IIB from registry-proxy. The IIB is a downstream release artifact. Using it would require the test cluster to have access to the internal Red Hat registry, which Prow AWS clusters do not have.
The lookup text box The text box on the FBC Summary tab accepts both formats: type an IIB number (e.g., 1187142) or an FBC SHA (e.g., 831c2ada). The dashboard finds the matching entry either way.
In simple terms Think of it like a receipt number vs. a barcode. The IIB number is the receipt you see and recognize. The FBC SHA is the barcode that the system scans internally. Both point to the same thing. You work with the receipt number; the system uses the barcode.
